# 장문 chunk 분할 정책 정적 비교 (2026-08-29, GPU 0)

권위 자료는 `_local/assets/golden/.../c3_performance/_config.json` 의 원문·설정이다.
대사 원문은 이 문서에 옮기지 않는다.

## 1. 현재 production 계획 재현 — 일치

현재 develop 코드로 계획하면 **18 segment / 141 chunk** 가 나오고,
chunk 별 production token 이 골든 실측과 **141/141 일치**한다. 계획 경로에 드리프트가 없다.

- 문장(종결부호) 123 · 문단 18 · 비어있지 않은 줄 18
- target token min 11 / 중앙 25 / max 33
- B envelope 대상 17곳, 전부 `paragraph` 경계. app gap 0 아닌 곳도 같은 17곳
  (문장 내부 chunk 경계의 gap 은 0 — 이전에 폐기한 "내부마다 0.4초" 가설이 다시 확인됐다)
- `generation_limit` 은 141 chunk 전부 **256** 이다

## 2. 안전 예산은 유도값이지 고정값이 아니다

ICL 은 참조를 매번 다시 말하므로 그 비용이 예산을 먼저 먹는다(실측 113.5 frame ≈ 9.08s).

```
ABS_LIMIT 256 − 참조 재발화 113.5 = 목표 헤드룸 142.5 frame
frames = 1.999*tok − 14.75  (골든 141 chunk 회귀) 를 역산
→ 목표 상한 78 token
```

현재 production 상한은 **33** 이다. 이 값은 `⌊(256−160)/2.9⌋` 로 얻은 것인데,
그 식은 `prod_tokens = 목표 전용` 을 전제한다. controlled-prefix ICL 에서는
`prod_tokens` 가 **참조+목표 결합값**이라 전제가 깨지고, 실제로 141 chunk 전부
동적 상한이 256 으로 clamp 된다. 즉 33 은 ICL 을 설명하지 못하는 상한이다.

## 3. 정책 비교

| 정책 | chunk | 상한 | token(min/중앙/max) | 참조 낭비 frame | 예상 시간 |
|---|---|---|---|---|---|
| A 현재 production | 141 | 33 | 11/25/33 | 16,003 | 80.0분 |
| B 문장부호 우선 | 153 | 33 | 11/24/33 | 17,365 | 85.4분 |
| C headroom 병합 | 45 | 78 | 21/63/77 | 5,107 | 37.0분 |
| D 문단 전체 | — | — | — | — | **PRECHECK_UNSAFE** |
| E 문단강제+안전병합 | 45 | 78 | 21/63/77 | 5,107 | 37.0분 |

- **D 는 GPU 생성 대상이 아니다.** 18 문단 전부 한도 초과(83~218 token)이며
  가장 짧은 문단조차 넘는다. 한도 초과 텍스트를 조용히 자르지 않는다.
- **C 와 E 는 이 원문에서 결과가 같다.** 문단 경계와 segment 경계가 일치하기 때문이며
  (문단 18 = segment 18), 문단 경계 강제가 추가 제약이 되지 않는다.
  원문 구조가 다르면 갈라질 수 있으므로 둘을 같은 정책으로 합치지 않는다.
- B 는 A 보다 chunk 가 늘어난다(문장 경계를 넘겨 병합하지 않으므로).

## 4. 확정 / 가설 / 미확정

**확정**
- 계획 재현 일치(141/141), D 부적합, C≡E(이 원문 한정), 참조 비용이 예산의 주 소비자
- A 기준 join 140곳 중 문장 내부가 123곳 — 사용자가 듣는 "끊김" 후보의 대부분

**가설(미검증)**
- chunk 를 141→45 로 줄이면 이음매가 줄어 연결부 어색함이 완화된다
- 참조 낭비가 16,003→5,107 frame 으로 줄어 생성 시간이 절반 이하가 된다

**미확정**
- 큰 chunk 가 음질·억양 일관성에 주는 영향. token 이 커지면 생성이 길어져
  중간에 흐트러질 여지도 있다. **정적 분석으로는 답할 수 없고 청취가 필요하다.**
- 상한 78 은 회귀 역산값이다. 실제 생성에서 안전한지는 GPU 실행으로 확인해야 한다.

## 5. 하지 않은 것

production 분할 정책을 바꾸지 않았다. 사용자 청취 승인 전에는 바꾸지 않는다.
