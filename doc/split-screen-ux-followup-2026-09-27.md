# 트랙 분할 화면 — 후속 UX 항목 (2026-09-27)

한 것**과 **아직 재지 않은 것**을 적어 둔다. 지금 고칠 항목이 아니라 다음에 볼 목록이다.

## 1. 긴 곡에서 분할선 손잡이가 겹친다

**무엇** — 분할선은 보이는 굵기 2px 에 **잡는 폭 20px** 짜리 투명 손잡이를 덧댄다.
분할선 둘이 화면에서 20px 안으로 붙으면 손잡이가 겹치고, **나중에 만든 쪽이 잡힌다.**
앞에 있는 선을 끌고 싶어도 뒤 선이 잡힐 수 있다.

**언제 실제로 걸리나** — 화면 폭 800px 기준 20px 은 전체 길이의 2.5%.
10분(600초) 곡이면 **15초 안에 두 지점**이 있을 때부터다.
곡 사이를 나누는 용도라면 드물지만, 구간을 잘게 나누는 쓰임에서는 흔하다.

**후보**
- 화면을 확대(zoom)할 수 있게 해서 붙은 지점을 벌린다 — 근본 해결이지만 범위가 크다.
- 겹칠 때만 손잡이를 좁힌다(이웃과의 간격에 맞춰 최대 20px).
- 목록 쪽에서 시간을 숫자로 고치는 길을 눈에 띄게 둔다 — 이미 있으나 끌기만큼 쓰이지 않는다.

★**음원 구간 자체를 넓혀서 해결하지 않는다.** 넓히면 저장되는 경계가 뭉툭해진다
(이번 수정에서 그렇게 하지 말라는 지시를 받았고, 그 판단이 맞다).

## 2. 긴 곡의 파형 메모리·그리기 성능을 재지 않았다

**무엇** — 파형은 `WaveSurfer` 가 `backend: 'WebAudio'` 로 **통째로 디코딩**해서 들고 있다.
지금까지 확인한 것은 **10초·42초 합성 음원**뿐이다.

**걱정되는 자리**
- 디코딩된 PCM 이 메모리에 그대로 남는다. 1시간짜리 무손실 음원이면 수백 MB 급이다.
- 분할선이 많아지면 그때마다 DOM 요소가 늘어난다(지금은 ID 별 갱신이라 다시 만들지는
  않는다 — 재생성 비용은 없앴지만 **개수 자체**는 재지 않았다).
- `무음 구간 자동 감지` 는 화면에서 프레임마다 RMS 를 돈다. 긴 곡에서 얼마나 걸리는지 모른다.

**재야 할 것** — 10분·30분·1시간 음원에서 (1) 불러오기 시각, (2) 렌더러 메모리 증가분,
(3) 분할선 50개·200개일 때의 조작 반응, (4) 자동 감지 소요 시간.
★추측으로 손대지 않는다. **재고 나서** 필요하면 고친다.

## 3. 저장 경로에서 아직 재지 않은 것

- **압축 원본**(mp3·m4a·opus) 에서 경계가 같은지 확인하지 않았다.
  이번 확인은 WAV 입력만 했다. 압축 원본은 ffmpeg 이 앞쪽 프레임부터 풀어야 하므로
  경계가 몇 밀리초 밀릴 수 있다 — **밀리는지 아닌지 재지 않았다.**
- **실제 긴 곡**(10분 이상) 에서의 분할 저장 소요 시간과 결과.
- 저장 폴더에 **같은 이름**이 이미 있을 때의 동작(덮어쓰는지, 비켜 가는지) 미확인.
- 트랙 이름에 파일 이름으로 쓸 수 없는 글자를 넣었을 때의 결과는 규칙
  (`split_markers.safe_label`)만 확인했고 **실제 저장으로는 확인하지 않았다.**

## 4. 이번 범위에서 의도적으로 뺀 것

- **앱을 껐다 켠 뒤의 편집 복원.** 메뉴 왕복까지만 보존한다(디스크에 쓰지 않는다).
- **확대/축소.** 위 1번의 근본 해결책이지만 이번 지시 범위 밖이다.
- **옛 작업 → 카드 가져오기.** 조사만 끝났다(`doc/legacy-to-cards-survey.md`).
  검수 대기 중이므로 착수하지 않는다.
