# 엔터 말끝 조사와 후처리 보존 (2026-10-12)

사용자 판정: 새 기준 목소리는 기존에 사용하던 느낌에 가까워졌으나, 엔터로 대사를 끊을 때 말끝이 급하게 끝난다. `---`로 발화를 늘릴 수 있는지 문의했다.

## 실제 근거

- 승인된 A–D 기준 음성의 24개 생성 조각, 연결 직전 조각, 최종 파일을 대조했다. 저장 지문을 확인했다.
- 연결 전후 프레임 수와 최종 대응 구간 길이는 24/24 같았다. 줄 사이 무음은 0.5초였다. 프레임 삭제로 줄어든 사례는 없었다.
- 기존 연결은 엔터 경계에서 앞 조각 마지막 20ms에 감쇠를 적용했다. 일부 조각에는 그 창에 소리가 남아 있어 추가로 약해졌다.
- 모델 반환부터 말미에 소리가 남은 조각도 있었다. 급한 종료와 일치하는 신호지만, 수치만으로 마지막 음절 누락을 확정하지 않는다.

## 구현

- Qwen 조립 경로에 말끝 보호를 명시적으로 켰다. 끝 20ms 중 -60dBFS(절대 진폭 0.001)를 넘는 샘플이 있으면 offset fade를 하지 않는다.
- 최종 Qwen 말끝도 같은 보호 조건으로 추가 감쇠를 막고 요청한 120ms 무음 패딩은 유지한다.
- 시작 처리는 유지한다. 이미 조용한 말끝의 기존 클릭 방지 처리도 유지한다. 전체 음량·속도·음높이·조각 순서·줄 사이 무음은 같은 처리다.
- 보호 횟수와 마지막 말끝 보호 여부를 결과·실행 기록에 남긴다. 기록에서 실제로 걸리지 않은 offset을 적용했다고 표시하지 않는다.
- 이 조건은 발음 완전성 판정기가 아니다. 모델이 만들지 않은 소리 복원이나 자의적인 끝음 연장을 하지 않는다.

## 청취 자료

`master/AudioForge/_local/테스트/결과/newline-tail-20261012/말끝비교듣기.html`

기존 생성 조각을 동일하게 재사용해 후처리만 비교했다. 목소리마다 참조·기존 전체·보존 전체와 각 줄 말미의 모델 원본·기존·보존 3단계가 있다. 기준 파일과 새 파일의 프레임 수가 같고, 발음 후보가 남은 보호 창은 연결 직전 배열에서 샘플 단위로 보존됨을 확인했다.

보호된 줄 끝: A 1곳, B 2곳, C 4곳, D 2곳. 마지막 줄은 D만 보호했다. 이것을 잘린 음절 10개로 해석하지 않는다.

## 열린 항목

- 첫 제한 환경 시도가 참조 준비 뒤 정체돼 해당 프로세스만 종료했다. 이후 두 시도는 GPU 여유 부족으로 생성 전에 중단됐다. 모든 시도 기록을 보존했다. 이후 여유 확보 뒤 아래 실제 비교 3개를 완료했다.
- 후처리 보존본의 사람 청취 대기. 실제 앱·IPC 경로는 이번에 실행하지 않았다.
- `---`를 사용자가 수동으로 넣는 해결 방식이나 마침표 자동 삽입은 제품에 추가하지 않았다.
- 개발 작업 파일에 구현했으며 커밋·배포 병합은 하지 않았다. 보류 파일 4개는 손대지 않았다.

## GPU 여유 확보 후 실제 비교

`master/AudioForge/_local/테스트/결과/newline-tail-20261012/generation-01/줄바꿈비교듣기.html`

- B 참조 8.845초·같은 원문 낱말·시작 seed 20261011·같은 모델과 말끝 보존 코드. 엔터 유지 / 엔터를 공백으로 바꿈 / 각 줄 마지막에 마침표 추가 3개를 새로 생성했다.
- 세 조건 모두 CUDA·참조 대사/억양 활용, 자동 대체 없음. 원본과 참조 지문 불변, 최종 파일과 실행 기록 지문·원문 대조 완료.
- 엔터 13.10초/6조각, 한 줄 9.56초/1조각, 마침표 14.06초/6조각. 한 줄은 강제 줄 간 쉼이 없고 후속 조각 seed 배정도 달라져 단일 원인의 우열을 확정할 수 없다.
- 엔터 조건은 생성 원본의 두 끝창에 큰 소리가 남았다. 마침표 조건도 `괜찮아.` 끝창에 소리가 남아, 마침표가 항상 자연스러운 종료를 보장한다고 결론내리지 않았다.
- 자동 받아쓰기: 엔터·한 줄은 공백/기호 제외 낱말 일치. 마침표는 `음`을 `응`으로 인식했다. 실제 발화 오류인지 사람 청취 필요.
- 각 생성 조각의 끝 원본을 따로 듣는 기능과 전체 파일 경로를 페이지에 제공했다. 사용자 청취 전, 말끝·음질 합격 판정 없음. 이번 생성 때문에 무관한 검사나 이미 통과한 114건을 반복하지 않았다.

## 웹 TTS 공식 문서 조사

- Azure/Google은 문장 구조(s/p)와 쉼(break)을 구분한다. Google은 완결된 문장을 s로 감싸고 긴 쉼을 문장 사이에 두기를 권한다.
  - https://learn.microsoft.com/en-us/azure/cognitive-services/speech-service/speech-synthesis-markup-structure
  - https://docs.cloud.google.com/text-to-speech/docs/ssml?hl=en
- ElevenLabs 입력 스트리밍은 문맥을 버퍼링하고 끝에서 flush로 남은 글의 생성을 요청한다. flush는 잘린 음성 복원이 아니다.
  - https://elevenlabs.io/docs/eleven-api/guides/how-to/websockets/realtime-tts
- 이전/다음 글과 이전/다음 요청 ID로 여러 생성의 연결감을 돕는 API가 있다. Qwen에 동일한 인자가 있다는 의미는 아니다.
  - https://elevenlabs.io/docs/api-reference/text-to-speech/convert
- 대시와 여러 대시도 쉼을 유도하는 방법으로 안내하지만 일관성은 낮고 모델에 따라 다르다. 사용자 `---` 아이디어를 근거 없는 것으로 취급하지 않는다. Qwen에서 말끝을 복원한다고 보장하지도 않는다.
  - https://elevenlabs.io/docs/help-center/product/core-capabilities/text-to-speech/how-can-i-add-pauses

개발 판단: 후처리 보존에 이어 표시용 엔터·문장 종결·생성 문맥·명시적인 쉼을 구분하는 구조를 검토한다. 이번에는 마침표 자동 삽입이나 외부 서비스 연결을 제품에 추가하지 않았다. 검색은 일반 기술 용어만 사용했으며 사용자 미디어는 전송하지 않았다.


## 문맥 유지와 안전한 줄 쉼 비교 경로 (2026-10-12, 청취 전)

사용자 판정: 엔터만 쓰면 잘림. 한 줄은 가장 자연스럽지만 중간 쉼이 부족함.
각 줄 끝 마침표 조건은 1·2줄이 자연스럽고 3~6줄은 끊김.

`AUDIOFORGE_DIAG_CONTEXT_LINES=1`로만 사용하는 비교 경로를 추가했다.
제품 기본 방식은 유지한다. 같은 화자·같은 연출, 일반 줄바꿈 2~12줄,
총 500글자 이하만 공백으로 이어 하나의 문맥으로 생성한다.
문단·명시 쉼·연출 변경은 거부하고, 실제 모델 청크가 둘 이상이면 결과를 발행하지 않는다.
원문은 요청에 남고 실제 보낸 글은 생성 기록에 남는다.

기존 단어 정렬과 한국어 정규화 코드를 재사용한다. 전체 대사가 일치하고,
양쪽 단어 시각이 유효하며 단어 사이에서 12ms 이상의 작은 신호 구간이 확인될 때만
목표 쉼에 부족한 무음을 삽입한다. 기존 샘플은 제거·페이드하지 않는다.
이는 보수적인 신호 규칙이며 음소 단위 안전성을 보장하는 정렬기는 아니다.
불확실한 경계는 원본을 보존하고 사유를 남긴다.
추가 쉼의 좌표는 `context-line-pauses.json`에 별도 기록하며 생성 조각의 위치와 구분한다.

기존 B 한 줄 생성본을 CPU 로컬 Whisper로 확인한 결과:
줄 경계 5곳 중 4곳은 단어 사이 간격을 확인하지 못했다.
나머지 1곳은 기존 무음 11973샘플, 추가 27샘플(24kHz, 약 1ms)이다.
따라서 이번 소리의 호흡 부족을 사후 무음 삽입만으로 해결하지 못했다.
이 파생 파일은 개선 합격본으로 제공하지 않는다.

다음 비교는 같은 B·대사·seed에서 문맥 유지 방식과
문맥 유지+각 줄 마침표 방식이다. GPU 여유 518MiB로 사전 검사에서 중단했으며
새 음성은 만들어지지 않았다. CPU 합성이나 다른 목소리로 대체하지 않았다.
