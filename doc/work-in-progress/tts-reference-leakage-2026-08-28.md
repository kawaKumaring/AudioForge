# 참조 음성 대사 혼입 — 진단 보고서 (2026-08-28)

대상: Qwen3-TTS-12Hz-0.6B-Base voice clone(ICL) 경로
계기: 사용자가 생성 음성에서 참조 대사 조각을 **직접 듣고 확정**. 당시 자동 검사는
`contamination_detected=false` 였다 — 그 판정은 위음성으로 확정됐다.

---

## 1. 결론

**확정 원인: conditioning echo — `ref_text` 가 `ref_audio` 에 없는 말을 담고 있으면,
talker 가 그 없는 말을 생성 구간 맨 앞에서 먼저 발음한 뒤 타깃 문장을 시작한다.**

prompt codec slicing 결함이 아니다. vocoder/후처리 결함도 아니다. 캐시·버퍼 잔류도 아니다.
셋 다 아래 수치로 각각 배제됐다.

실패한 실행에서 이 조건이 성립한 경위:
참조 클립은 원본 `vocals.wav` 의 **14.0~23.0초 고정 창**으로 잘렸다. 시작 14.0초는 무음 구간
안이지만 **끝 23.0초는 발화 한가운데**다(무음 런은 22.57~22.83, 23.47~23.73 — 23.0 은 어느
쪽에도 속하지 않는다). 반면 `ref_text` 는 그 창에 걸친 전사 세그먼트 4개를 **통째로** 이어
붙여 만들어졌다. 그래서 오디오에는 없는 마지막 음절들이 전사에만 남았다.

측정으로 확인한 어긋남의 크기: 참조 클립(9.000초)의 자체 ASR 은 47음절 중 44음절만 인식했고
(`sub 2 / del 3 / ins 0`, CER 0.106), 마지막 인식 단어는 8.98초에 끝난다 — 즉 클립은 문장이
끝나기 전에 잘렸다. 수동 전사에만 남은 꼬리는 3음절이다.

그 결과가 `happy_raw.wav` 0.00~0.66초 구간이다. 이 구간의 ASR 은 참조 문장의 마지막
어절(6음절)과 일치했고, 타깃 문장은 0.80초부터 시작한다.

## 2. 통제실험 — 마커로 논증 없이 확정

원본 참조는 어휘가 실제 발화라 "우연히 비슷한 말"과 구분이 어렵다. 그래서 원본에도 타깃에도
없는 **고유 마커 문장**을 참조 전사 맨 끝에 붙이고, 출력에 그 어휘가 나오는지만 봤다.

- 마커 A: `보랏빛 낙타가 우산을 삼켰다.` (검출 토큰 보랏/랏빛/낙타/우산/삼켰)
- 마커 B: `무쇠 해오라기가 벽돌을 쌓았다.` (검출 토큰 무쇠/해오/오라/라기/벽돌/쌓았)

참조 오디오는 **양쪽 경계가 무음 한가운데**인 6.515초 클립(원본 13.97~20.485초)으로 고정했고,
`ref_text = 클립 전사 + 마커 문장` 으로 두었다. **마커는 전사에만 있고 오디오에는 없다.**

확정 실험 4개(프로세스 1회 호출 = 실험 1개, 고정 seed A=20260828 / B=20260829):

```
E1_freshA        새 프로세스, 마커 A 1회
E2_freshB        새 프로세스, 마커 B 1회
E3_seqAB         한 프로세스, A 생성 후 이어서 B 생성
E4_freshBalone   새 프로세스, 마커 B 단독 1회
```

### GPU 실행 게이트
실행 직전 10초 간격 한 쌍만 측정. free 14911 MiB / util 0·0 / ML compute 프로세스 0 →
free ≥8GB, 평균 ≤5%, 최대 ≤10%, 외부 compute 없음 전부 충족.
(직전 시도에서는 평균 8.5% · 최대 16% 로 미충족이어서 재측정 없이 중단했고, 그 사이에는
GPU 없이 되는 증거만 채웠다.)

## 3. 7단계 증거표

단계 정의와 vendor 구조의 중요한 사실 하나:
**이 vendor 에는 토큰 도메인 slicing 이 없다.** `generate_voice_clone` 은
`codes_for_decode = concat(ref_code, generated)` 로 **프롬프트를 붙여서** 보코더에 넣고,
그 다음 PCM 도메인에서 비율 절단 `wav[cut:]` 로 참조 구간을 걷어낸다. 즉 2번 단계는
"프롬프트가 제거된 토큰"이 아니라 "프롬프트가 더해진 토큰"이며, 제거는 3번 이후에 일어난다.

E1 (마커 A, fresh):
```
0A 참조 전처리 PCM      float32 [156361]      6.515s   sha 7a45f4a0
0B prompt codec token   int64   [82, 16]      82프레임  sha eb18c776
0B prompt text ids      int64   [1, 49]       49토큰    sha 3f876414
1  generate 반환 토큰    int64   [70, 16]      70프레임  sha 488bfdf5
2  보코더 입력 토큰      int64   [152, 16]     152프레임 sha e216bbde   (= 82 + 70, 검증 True)
3  보코더 직후 PCM       float32 [291840]      12.16s   sha bb35c759
4  후처리 직후 PCM       float32 [134400]      5.60s    sha 41bf9aaa
5  최종 저장 WAV         268844 bytes          5.60s    sha 64033ca2
```

E2 / E4 (마커 B, fresh) — 두 실행이 완전히 동일:
```
0A  float32 [156361] 6.515s  sha 7a45f4a0     0B codec int64 [82,16]  sha eb18c776
0B text ids int64 [1,49]     sha af29435b     1  int64 [74,16]        sha 81398aea
2   int64 [156,16]           sha 60e698bc     3  float32 [299520] 12.48s sha f3f2a7fc
4   float32 [142080] 5.92s   sha d8647b88     5  284204 bytes 5.92s   sha de28d993
```

E3 (한 프로세스, A→B): A 부분은 E1 과, B 부분은 E2/E4 와 **모든 단계 해시가 동일**하다.

슬라이싱 수치(4개 실행 전부 동일): `slice_index = 157440` 샘플, `exact_ref = 82 × 1920 =
157440`, **`slice_error = 0` 샘플**. 보코더 입력이 `ref_code ++ generated` 임도 배열 비교로
검증했다(`s2_equals_ref_plus_s1 = True`).

## 4. 최초 마커 등장 단계

```
0A 참조 전처리 PCM     마커 없음   (ASR: A토큰 0개, B토큰 0개)
0B prompt codec        마커 불가   (0A 를 encode 한 것 — 0A 에 없으면 여기에도 없다)
1  generate 반환 토큰   마커 있음   ★ 최초 등장
3  보코더 직후 PCM      마커 있음
5  최종 WAV             마커 있음
```

1번에 이미 있다는 직접 증거: 별도 실행에서 **참조 prefix 없이 생성 토큰만 보코더에 통과**시킨
`s3_gen_only.wav` 를 ASR 했더니 마커 5토큰이 전부 나왔다. 그 신호에는 참조 codec 이 한 프레임도
섞여 있지 않으므로, 마커는 talker 가 만들어낸 토큰 안에 있다.

즉 마커는 **모델이 생성한 토큰에서 처음 등장**한다. 보코더도 후처리도 마커를 만들지 않았다.

---

## 5. 직접 토큰 중복률 (판정의 갈림길)

`0B prompt codec` 의 **꼬리** K프레임과 `2번 보코더 입력 토큰`의 **post-slice 머리**
(= 생성 구간 첫 K프레임) 를 프레임 단위로 직접 비교했다.

```
K=5    exact_frame 0/5    0.0000    codebook0 0.0000    setwise 0.0000
K=10   exact_frame 0/10   0.0000    codebook0 0.0000    setwise 0.0000
K=20   exact_frame 0/20   0.0000    codebook0 0.0000    setwise 0.0000
```
4개 실행 전부 동일하게 **0.0000**.

판정 기준에 대입하면:
- 직접 토큰 중복 높음 → slicing 오류 → **해당 없음(0.0000)**
- 직접 중복 낮은데 ASR 에는 동일 마커 → **conditioning echo → 이쪽으로 확정**

보조 증거로 파형 NCC 도 함께 재 두었다. 마커 혼입이 확인된 출력에서도 500 ms 창 NCC 최대는
0.47~0.69 로, 혼입이 없는 대조군(0.51~0.68)과 겹친다. **파형은 복사되지 않았고, NCC 는 이
종류의 혼입을 구분하지 못한다** — 모델이 참조 내용을 다시 합성하기 때문이다.

## 6. fresh / sequential 차이

같은 마커의 최종 WAV 해시:
```
마커 A   E1_freshA 64033ca2   |  E3_seqAB(1번째) 64033ca2      → 동일
마커 B   E2_freshB de28d993   |  E3_seqAB(2번째) de28d993   |  E4_freshBalone de28d993   → 동일
```

E3 에서 B 는 같은 프로세스에서 A 를 생성한 **직후**에 만들어졌는데도, fresh 프로세스의 B 와
**바이트 단위로 같다**. 그리고 E3 의 B 출력에서 마커 A 어휘는 **0개** 검출됐다.

→ 앞선 생성이 뒤 생성에 남기는 영향은 없다. **캐시·버퍼 잔류 아님.**

## 7. 시작 2초 ASR

각 실행의 최종 WAV 앞 2.0초만 잘라 따로 전사했다(전체 디코딩이 앞머리 조각을 삼키는 것을
피하려는 목적).
```
E1_freshA       마커 A 5토큰 검출 / 마커 B 0
E2_freshB       마커 B 3토큰 검출 / 마커 A 0
E3_seqAB  #A    마커 A 5토큰 검출 / 마커 B 0
E3_seqAB  #B    마커 B 3토큰 검출 / 마커 A 0
E4_freshBalone  마커 B 3토큰 검출 / 마커 A 0
```
마커는 예외 없이 **출력의 맨 앞 2초**에 있다. 각 실행은 **자기 참조의 마커만** 뱉는다.

원본 실패 실행(`happy_raw.wav`)에도 같은 방법을 적용했더니, 앞 1.5초 전사에서 참조 문장 끝의
3음절 n-gram 4개가 검출됐다. 전체 파일 전사에서는 그 조각이 문맥에 흡수돼 사라진다 —
**기존 검사가 위음성을 낸 두 번째 이유가 이것이다.**

## 8. 원래 10개 진단 결과

1. **2~3음절·자모 n-gram 비교** — `happy` 전체 전사에서 참조에만 있는 3음절 n-gram 4개,
   2음절 5개, 자모 6-gram 8개 검출. 4음절 이상만 보던 기존 검사로는 0개. `angry`/`sad` 는 0개.
2. **조사·어미 제외 reference-only 단어** — 세 감정 모두 0개. 혼입이 어절 단위로 온전히
   재현되지 않고 조각으로 오기 때문에, 이 지표 단독으로는 검출력이 없다.
3. **머리/꼬리 1.5초 분리 ASR** — `happy` 머리에서 8음절(전부 참조 유래), 꼬리 0.
   `angry` 머리 3음절·`sad` 머리 3음절은 전부 타깃 문장. 통제실험도 같은 결론(§7).
4. **log-mel DTW / 대각 매칭** — 참조 대 출력 600 ms 최고 0.80~0.82.
   대조군(출력끼리) 0.79~0.89 로 더 높다. **변별력 없음.**
5. **파형 NCC** — 전체 1창 0.060/0.071/0.093. 창 단위 최대는 100 ms 0.90 / 200 ms 0.79~0.89 /
   **500 ms 0.467·0.493·0.485**. 대조군(출력끼리) 200 ms 최대 0.727~0.801.
   500 ms 에서 임계 0.90 을 넘는 창은 **0개**. 파형 복사 없음.
   `happy` 머리 200 ms 를 참조 머리에 정렬한 NCC 는 0.0165 — 프롬프트 오디오가 남아 있지 않다.
6. **codec prompt 토큰 수와 출력 slicing** — hop 1920(= 24000/12.5Hz).
   참조 9.000초 → `ceil(216000/1920) = 113` 프레임. 관측 길이 3건을 전수 탐색으로 역산해도
   `iters − codes = 1`(종료 토큰 1개)이 유일 해였고 113 이 후보에 포함된다.
   절단 오차는 0 또는 **−1 샘플**(angry 의 115201 이라는 홀수 길이가 그 −1 의 흔적).
   −1 샘플 = 0.042 ms. 들리는 혼입의 원인이 될 수 없다.
7. **생성 토큰에서 prompt codec 이 제거되는 위치** — 토큰 도메인에서는 제거되지 않는다.
   `talker_codes_list` 자체에 참조가 없고, 보코더 입력에서 참조가 **더해졌다가**, PCM 절단으로
   빠진다. 통제실험 4건 전부 `slice_error = 0`.
8. **ref_audio 9초 ↔ ref_text 63자 정렬** — 어긋남 확인(§1). 클립 ASR 44음절 vs 전사 47음절,
   `del 3`, 마지막 인식 단어 종료 8.98초 / 클립 9.000초, 꼬리 무음 **0.000초**.
   region.json 의 `segments_in_region: 4` 와 원본 타임스탬프를 대조하면 4번째 세그먼트가
   창 경계를 넘어간다.
9. **vendor 반환값이 prompt audio 를 포함하는가** — 포함하지 않는다.
   출력 길이 = 생성 프레임 × 1920 과 정확히 일치(통제실험 4건 + 원본 3건).
10. **target text 와 ref_text 의 분리** — 유지된다. `tts_worker` 는
    `segments[*] = {"text": …, "ref_text": …}` 로 분리해 담고, `qwen_bridge._generate_segment`
    는 `text=seg["text"]`, `ref_text=ref_text` 로 각각 넘긴다. 두 값이 섞이는 경로는 없다.
    통제실험이 이를 다시 확인한다 — 0A·0B codec 해시가 실행 간 완전히 동일하고
    **0B text ids 해시만 다르며**(A `3f876414` / B `af29435b`), 새어 나온 마커는 텍스트를 따라간다.

## 9. 무엇을 수정했고 무엇을 일부러 두었는가

수정한 것 — `python/reference_leakage.py`(신규, 순수 numpy 계측):
- `boundary_truncation()` 참조 클립이 경계에서 발화 중인가. **원인 쪽 신호.**
- `short_ngram_leaks()` 2~3음절 조각. 기존 검사의 사각지대(§8-1).
- `waveform_copy_scan()` 파형 그대로 복사(NCC). ASR 로 안 잡히는 종류.

배선 — `reference_region.analyze_region()` 에 경계 절단 경고와 측정 필드 추가.
구간을 고르는 자리에서 "끝이 말 도중"이라고 알려주지 않으면, 전사에만 있는 꼬리가 그대로
ICL 프롬프트로 들어간다. 실제 실패 참조는 `tail_truncated = True`(tail −31.81 dBFS),
통제실험용 깨끗한 클립은 `False`(tail −45.54 dBFS) 로 갈린다.

일부러 하지 않은 것:
- **vendor 슬라이싱의 −1 샘플 오차를 고치지 않았다.** 0.042 ms 이고 vendor 수정 금지 대상이며,
  들리는 혼입과 무관하다. 고치면 원인을 고친 것처럼 보여 오히려 해롭다.
- **수동 전사를 자동으로 잘라내지 않았다.** 수동 전사는 Whisper 오인식을 사람이 고치는 수단이라,
  ASR 과 다르다는 이유로 사용자의 글자를 지우면 정반대 방향으로 망가진다.
- **fade·앞부분 삭제·무음 삽입 같은 은폐를 하지 않았다.** 혼입 구간을 잘라내면 증상만 사라진다.
- **`x_vector_only` 강등을 기본값으로 만들지 않았다.** ICL 을 끄는 것은 회피지 수정이 아니다.

## 10. 확인하지 못한 것 (정직하게)

- **코드 수정 전/후의 WAV 쌍을 만들지 못했다.** 이번 production 수정은 구간 선택 시점의
  예방 경고이지 생성 경로를 바꾸는 변경이 아니라, "같은 config 로 수정 전/후" 비교가
  성립하지 않는다. 대신 **조건 대조 쌍**이 있다:
