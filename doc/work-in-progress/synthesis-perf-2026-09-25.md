# 합성 속도 — 재는 것부터

## 왜 여기서 시작하나

실사용 로그를 집계했더니 완료된 합성이 **5건**(중앙 71초, 최대 298초, 나흘치)이었다.
이 표본으로 개선 항목을 고르면 추측이 된다.

그래서 구현을 읽어 병목을 찾는 조사를 돌렸고, **반증 검증이 순위를 뒤집었다.**

## ★저장소 안에 이미 실측이 있었다

조사가 세운 우선순위는 "시간을 나눌 수 없다" 는 전제 위에 있었는데, 저장소에 남은
실행 기록 3건이 그 전제를 깼다.

- 기본 모드 1조각: 총 136.2초 / 생성 88.9초(**65.3%**) / 생성 밖 47.2초
- 기본 모드 4조각: 총 80.1초 / 생성 68.3초(**85.3%**) / 생성 밖 11.8초
- 참조 억양 5조각: 총 68.1초 / 생성 51.5초(**75.6%**) / 생성 밖 16.6초

**시간의 65~85%가 생성 루프 안에 있다.** 그러므로 생성 밖을 건드리는 개선
(참조 재인코딩 줄이기·프로세스 상주)은 나머지 15~35%를 나눠 먹는 싸움이고,
상한이 이미 잡힌다 — 참조 재사용은 조각당 몇 초, 상주 프로세스는 웜 기준 12초 남짓이다.

그리고 상주 프로세스는 **위험이 이득보다 크다**: 2.5GB 를 작업 사이에도 붙들면
이 앱이 스스로 정한 양보 정책(여유 4000MB 미만이면 CPU 로 내려간다)과
ComfyUI 병행 전제를 정면으로 깬다. CPU 로 떨어지면 문장당 30초라 개선이 아니라 재앙이다.

## ★생성 루프 안에서 확인한 낭비

벤더가 코덱 프레임마다 부르는 예측기에 `output_hidden_states=True` 를 준다.
그런데 결과에서 읽는 것은 `.sequences` 뿐이고, 은닉 상태는 **한 번도 쓰이지 않는다**
(바로 아래에서 임베딩으로 새로 만든다).

12Hz 기준 20초 음성이면 240 프레임 — 매 프레임마다 전 레이어 은닉 상태를 쌓고 버린다.
★**아직 고치지 않았다.** 재기 전에는 고치지 않는다.

## 이번에 한 것: 재는 자를 채웠다

재는 비용은 **이미 치르고 있었다** — 브리지가 단계마다 경과를 실어 보내고 있었고,
기록기에는 `stage_elapsed` 칸이 있었다. 문제는 둘 다 쓰이지 않은 것이다:
부모가 그 숫자를 읽지 않고 버렸고, 기록 칸은 **부르는 곳이 0건**이라 언제나 빈 배열이었다.

이제 네 칸이 남는다.

- `model_load` — 프로세스를 띄워 모델이 올라오기까지(**부모 시계**).
  파이썬 기동·torch import·가중치 읽기가 전부 여기 들어간다.
- `bridge_loaded` — 브리지가 제 시계로 잰 적재(**제가 뜬 뒤부터**).
- `bridge_generating` — 생성 시작까지.
- `run_job` — 전체. 조각별 생성 합과 견주면 "생성 밖" 이 바로 나온다.

★**두 시계를 섞지 않는다.** 부모는 "프로세스를 띄운 뒤" 를, 브리지는 "제가 뜬 뒤" 를
잰다. 브리지 값에는 기동·import 가 들어 있지 않다. 한 이름으로 합치면 숫자를 읽을 수 없다.

★없는 값을 0으로 적지 않는다 — 안 걸린 것처럼 보이는 쪽이 더 나쁘다.

## 다음 순서

1. 같은 대본·같은 참조·고정 씨앗으로 연속 2회씩 돌려 기준선을 잡는다.
   찬 실행과 더운 실행의 차이가 그대로 나온다.
2. 그 숫자로 `output_hidden_states` 낭비의 크기를 확정한다.
3. 고친 뒤 **같은 씨앗에서 결과 해시가 완전히 같은지** 확인한다.
   다르면 되돌린다 — 소리가 바뀌는 속도 개선은 개선이 아니다.

★참조 음성은 사용자 미디어를 쓰지 않는다. 앱에 있는 한국어 엔진으로 만들어 쓴다.

## 검증
게이트 **통과 9 · 실패 0**. 계측 계약 검사 7건.

# 실측 결과 (2026-09-25, 사용자 승인 후 실제 합성 수행)

참조 음성은 **사용자 파일을 쓰지 않고** 앱의 한국어 엔진으로 만들었다.
씨앗 고정, 앱과 같은 파이썬, 같은 참조.

## 기준선 — 시간이 어디로 가는가

짧은 대본(1조각): 벽시계 21.3 / 21.9초 · 적재 8.3 / 8.3 · 생성 9.8 / 10.5
긴 대본(1조각): 벽시계 65.8 / 63.9초 · 적재 8.4 / 8.7 · 생성 54.2 / 52.0

- **생성 밖 고정비가 11.5초로 일정**하고, 그중 **적재가 8.4초**다.
- 짧은 합성에서는 적재가 **전체의 40%**, 긴 합성에서는 13%다.
- 생성은 대본 길이에 비례한다(짧은 쪽 10초, 긴 쪽 53초).

★**첫 실행은 적재가 35.5초였다.** 파일 캐시가 차가울 때다 — 데워지면 8.4초로 일정해진다.
  앱을 오래 안 쓰다 처음 합성하면 그 35초를 다시 낸다. 이것이 사용자가 체감하는 "처음이 느리다" 다.

## ★시도했으나 **이득이 없어 되돌린 것** — 은닉 상태 생략

벤더가 코덱 프레임마다 은닉 상태를 전부 쌓는데 결과에서 한 번도 읽지 않는다.
이론적으로는 명백한 낭비다. 감싸서 끄고 재 봤다.

1차(각 2회): 생성 시간 평균 **−1.5%**. 그런데 회차 간 변동이 4%라 판단 불가.
2차(같은 대본 8회, **켜고 끄기를 번갈아**): 은닉 유지 중앙 52.62초, 생략 중앙 52.23초 —
**차이 +0.7%**, 개별 값이 51.1~57.3초로 12% 퍼져 있다.

**결론: 실재하는 낭비지만 측정 가능한 이득이 없다.** 되돌렸다.

★왜 이론과 달랐나: 그 예측기는 프레임마다 몇 스텝만 도는 **작은** 서브모델이라,
쌓이는 은닉 상태의 양이 전체 계산에 비하면 미미했다.

★**소리는 8회 내내 완전히 같았다**(해시 한 종류). 즉 안전한 변경이긴 했다.
그래도 남기지 않는다 — **재서 이득이 없는 최적화를 코드에 두면**, 다음 사람이
"이게 왜 있지" 를 모른 채 유지 비용만 낸다. 대신 시도했다는 사실을 여기 적어
같은 실험을 다시 하지 않게 한다.

## 남은 후보와 각각의 상한

- **적재 8.4초/작업** — 짧은 합성의 40%. 프로세스를 살려 두면 없앨 수 있지만,
  2.5GB 를 작업 사이에 붙들어 앱의 GPU 양보 정책(여유 4GB 미만이면 CPU)과
  ComfyUI 병행 전제를 깬다. CPU 로 떨어지면 문장당 30초라 **개선이 아니라 재앙**이다.
  하려면 유휴 해제와 다른 GPU 작업 전 강제 반납이 반드시 함께 와야 한다.
- **조각마다 참조 재인코딩** — 이번 벤치는 두 대본 모두 **1조각**이라 이 항목이
  드러나지 않았다. 이득은 조각 수에 비례하므로 **조각이 여럿인 재료로 다시 재야** 한다.
- **생성 자체** — 시간의 대부분이지만 줄이려면 배치 생성이나 모델 수준 변경이고,
  둘 다 소리가 바뀔 수 있다. 품질을 깎는 개선은 개선이 아니다.

## 이번에 남긴 것

- `python/bench_tts.py` — 사용자 미디어 없이 합성 속도를 재는 자. 씨앗 고정,
  결과 해시 비교, 찬/더운 구분.
- 계약 검사 8건 — 특히 "사용자 파일을 받는 통로가 없다" 와 "결과 해시를 남긴다".
  ★속도만 재고 소리를 안 보면 **소리가 바뀐 개선을 개선으로 착각한다.**

## 검증
게이트 **통과 9 · 실패 0**. 실제 합성 12회 수행(GPU), 결과 해시 전부 일치.

# 3차 — **내 가설이 틀렸고, 병목의 정체가 바뀌었다**

## 세우고 곧바로 무너진 가설

"찬 시작 36초는 파일 캐시가 차가워서다 → 앱 켤 때 미리 데우면 된다" 고 제안했다.
착수 전에 확인했더니 **틀렸다.**

이 장비의 디스크는 순차 읽기 **1450 MB/s** 다(15.8GB 를 10.9초에 읽었다).
가중치 2.5GB 를 차갑게 읽어도 **1.7초**다 — 27초를 설명하지 못한다.
GPU 커널 캐시도 어제 이후 갱신이 없어 커널 컴파일도 아니다.

★**원인을 모른 채 "미리 데우기" 를 만들었다면**, 듣는지도 모르는 코드가 남고
  유지 비용만 늘었을 것이다. 바로 앞에서 세 번 연속 겪은 일이다.

## 대신 확실히 잴 수 있는 것을 했다 — 적재를 쪼갰다

브리지는 가중치를 읽기 **직전**에도 경과를 보내고 있었다(`stage=loading`).
그 한 칸을 주우니 적재 8.4초가 갈라졌다.

- **import(torch + 엔진 패키지): 5.66 / 6.14초 — 70%**
- 가중치 읽기 + GPU 올리기: 2.47 / 2.56초 — 30%

## ★병목은 가중치가 아니라 import 였다

통째로 보면 "모델이 크구나" 로 읽힌다. 갈라 보니 **매 합성마다 새 프로세스가**
**torch 를 처음부터 다시 읽는 6초**가 진짜였다.

그리고 이것이 찬 시작 36초의 후보이기도 하다 — torch 패키지는 **수천 개의 작은**
**파일**이라, 순차 1450MB/s 와 무관하게 처음 읽을 때 느리다. 2.5GB 한 덩어리를
읽는 것과 성질이 다르다. (★이 연결은 아직 **추정**이다. 찬 상태를 만들 수단이 없어
확인하지 못했다.)

## 이것이 바꾸는 것: "상주" 의 뜻이 달라진다

1차 조사는 "브리지를 살려 두자" 를 제안했고 나는 위험하다고 물렸다 —
모델 2.5GB 가 VRAM 에 상주해 GPU 양보 정책을 깨기 때문이다. 그 판단은 유효하다.

그런데 이제 **다른 선택지가 보인다**: 모델은 올리지 않고 **import 만 마친 프로세스**를
대기시키는 것. VRAM 을 한 바이트도 안 쓰고, 작업이 오면 가중치 2.5초만 들인다.

- 이득: 작업마다 **6초**. 짧은 합성 21초 기준 **28%**.
- VRAM 위험: **없음**(모델 미적재).
- 비용: 프로세스 수명 관리와 통신 규약 변경 — **구조 공사다.**
  지금 브리지는 stdin 을 끝까지 읽고 한 작업 뒤 종료하는 규약이다.

★아직 하지 않았다. 구조를 바꾸는 일이라 결정이 필요하다.

## 검증
게이트 **통과 9 · 실패 0**. 계측 계약 검사 11건. 실제 합성 누적 18회.

# 4차 — 추정이 확정됐고, **처음 한 번**을 배경으로 옮겼다

## 추정이 실측으로 확정됐다

브리지 venv 에서 import 만 세 번 재 봤다.

- 1회차(찬): torch 6.70초 + 엔진 패키지 19.16초 = **25.86초**
- 2회차(더운): 1.62 + 4.20 = **5.83초**
- 3회차(더운): 1.64 + 4.19 = **5.83초**

두 가지가 한 번에 확정됐다.

1. **더운 import 5.83초**(편차 0.01초)가 앞서 잰 `bridge_import` 5.66~6.14초와 일치.
   → **파일 캐시와 무관한, 프로세스마다 드는 CPU 비용**이다. 미리 데워도 안 줄어든다.
2. **찬 import 25.9초**는 더운 것보다 20초 많다. 찬 시작 35.5초 − 더운 8.4초 = 27초와
   거의 같다. → **찬 시작이 느린 원인이 import 였다**(3차의 추정이 확정됐다).

## 그래서 길이 둘로 갈린다

- **처음 한 번 20초** → 배경으로 옮길 수 있다. 구조 변경 없음, 위험 없음. **이번에 했다.**
- **매 작업 5.8초** → 프로세스를 상주시켜야 없앤다. 구조 공사. **별도 설계 중.**

두 가지는 서로 다른 문제를 푼다. 섞어서 말하지 않는다.

## 한 것: 앱 기동 때 배경에서 한 번 데운다

`src/main/services/bridge-warmup.ts`. 창을 만든 **뒤** 배경으로 띄우고 기다리지 않는다.

★**모델은 올리지 않는다.** `import torch, qwen_tts` 뒤에도 `torch.cuda.is_initialized()`
가 False 이고 VRAM 이 변하지 않는 것을 실측으로 확인했다(3064 → 3098 → 3093 MiB, 잡음 수준).
그래서 GPU 양보 정책도 ComfyUI 병행 전제도 건드리지 않는다.

실동작 확인: 시작 후 **12ms** 에 반환(기동을 막지 않음), 배경에서 9.4초 만에 완료.

규칙 넷을 검사로 박았다 — 모델을 안 올린다 / 아무것도 만들지 않는다 /
건너뛰면 사유를 남긴다 / **과장하지 않는다**(매 작업 이득을 약속하지 않는다는 것까지 검사한다).

끄는 법: `AUDIOFORGE_NO_WARMUP=1`. 검사 실행(E2E)에서는 자동으로 건너뛴다.

## 남는 한계

- 실제 사용자 환경에서 **찬 상태**를 만들 수단이 없어, "첫 합성이 20초 빨라진다" 를
  끝까지 확인하지는 못했다. 확인된 것은 (a) 찬 import 가 25.9초라는 것,
  (b) 데우기가 실제로 배경에서 돌고 앱을 막지 않는다는 것이다.
- 앱을 켜자마자 합성하면 데우기가 아직 안 끝나 이득이 부분적이다.

## 검증
게이트 **통과 20 · 실패 0 · 건너뜀 3**. 계약 검사 14건.

# 5차 — 상주 설계 검증과 **성능 작업의 매듭**

## ★내가 한 약속을 정정한다

"프로세스를 상주시키면 작업마다 5.8초, 짧은 합성의 28%" 라고 적었다.
설계를 네 갈래로 나눠 검증한 결과 **그 이득은 가장 큰 공사에서만 난다.**

- 브리지가 여러 작업을 받게만 하면 → 단발 합성 이득 **0**(작업이 하나뿐이니까)
- 부모 파이썬이 핸들을 재사용하면 → 단발 이득 **0**, 대신 더빙·재시도 경로에서만 회수
- **Electron 이 소유해야** 단발 합성에서 5.8초가 난다 — 그런데 그때 브리지가
  작업의 프로세스 트리 **밖**으로 나가고, 전송로 신설·취소 판정 변경·
  작업별 값(run-id)의 env→payload 이전·헤드리스 폴백이 **동시에** 움직인다.
  이 저장소에 그런 선례가 없다.

## 검증이 찾은 막는 위험 둘 (착수 전 반드시)

1. **성공한 작업이 죽는다.** 부모의 수신 루프는 `result` 를 받아도 끊지 않는다 —
   유일한 탈출이 프로세스 종료다. 상주시키면 결과를 손에 쥔 채 280초 무응답
   판정으로 들어가고, GPU 가 한가하면 유예도 안 걸려 트리를 죽인다.
2. **작업별 값이 굳는다.** run-id 가 spawn env 로 흐르므로 상주 프로세스는
   첫 작업의 id 를 영원히 쓴다. 진단 기록이 엉뚱한 폴더로 간다.

★그리고 "대기 중 VRAM 0" 은 **첫 작업 뒤에는 거짓**이다 — torch 는 CUDA 를 한 번
  쓰면 컨텍스트를 프로세스가 죽을 때까지 들고 있다. 지금은 죽어서 OS 가 회수한다.

## ★조사 결과를 그대로 믿었으면 잘못된 코드를 심을 뻔했다

한 갈래가 "transformers 가 끌어오는 scikit-learn 을 가리면 import 가 5.31→4.35초
로 줄었다(실측)" 고 보고했다. 직접 확인했다.

- scikit-learn 단독 import 는 **1.47초**가 맞다.
- 그런데 `transformers` 는 `find_spec("sklearn") is not None` 으로 **가용성만** 본다.
- 막는 방법이 셋인데 전부 안 된다 — 예외를 던지면 import 가 통째로 깨지고,
  그냥 넘기면 안 막히고, 가짜로 있다고 하면 **transformers 가 있다고 믿는다.**

실제로 막아 보니 `import qwen_tts` 가 실패했다. **이 최적화는 성립하지 않는다.**

## 남은 후보의 상한 — 이미 있는 숫자로 계산된다

"브리지를 먼저 띄워 import 를 부모의 준비와 겹치기" 가 마지막 후보였다.
부모가 브리지 밖에서 쓰는 시간을 14회 실측에서 뽑으면 **2.1~2.4초로 일정**하고,
그중 일부는 생성 **뒤** 마감이다. 즉 겹칠 수 있는 최대가 2.3초 미만이고
실제로는 1초 안팎이다. 5.8초 중 그만큼만 회수된다.

## 결론 — 여기서 매듭짓는다

| 후보 | 실측 이득 | 처분 |
|---|---|---|
| 은닉 상태 생략 | +0.7%(잡음) | 되돌림 |
| 참조 재인코딩 | 0.05초 | 안 함 |
| 조각당 고정비 | 존재하지 않음 | 해당 없음 |
| scikit-learn 가리기 | 방법이 성립 안 함 | 접음 |
| import 를 준비와 겹치기 | **< 2.3초** | 값어치 낮음 |
| 찬 시작 미리 데우기 | **20초** | **적용함** |
| 상주(Electron 소유) | 5.8초/작업 | **별도 결정** — 위험 큼 |

큰 것 하나를 얻었고 나머지는 전부 잡음이거나 큰 공사다.
**이론적 낭비가 측정 가능한 비용이 아니었던 경우가 네 번**이었다.

★다시 성능을 볼 때 쓸 것은 이 문서가 아니라 **`bench_tts.py` 와 단계 기록**이다.
  숫자는 장비·판이 바뀌면 달라진다. 자는 남는다.

## 검증
게이트 **통과 20 · 실패 0 · 건너뜀 3**. 실제 합성 누적 18회 + import 측정 12회.
