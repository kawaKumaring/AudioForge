# 합성 속도 — 재는 것부터

## 왜 여기서 시작하나

실사용 로그를 집계했더니 완료된 합성이 **5건**(중앙 71초, 최대 298초, 나흘치)이었다.
이 표본으로 개선 항목을 고르면 추측이 된다.

그래서 구현을 읽어 병목을 찾는 조사를 돌렸고, **반증 검증이 순위를 뒤집었다.**

## ★저장소 안에 이미 실측이 있었다

조사가 세운 우선순위는 "시간을 나눌 수 없다" 는 전제 위에 있었는데, 저장소에 남은
실행 기록 3건이 그 전제를 깼다.

- 기본 모드 1조각: 총 136.2초 / 생성 88.9초(**65.3%**) / 생성 밖 47.2초
- 기본 모드 4조각: 총 80.1초 / 생성 68.3초(**85.3%**) / 생성 밖 11.8초
- 참조 억양 5조각: 총 68.1초 / 생성 51.5초(**75.6%**) / 생성 밖 16.6초

**시간의 65~85%가 생성 루프 안에 있다.** 그러므로 생성 밖을 건드리는 개선
(참조 재인코딩 줄이기·프로세스 상주)은 나머지 15~35%를 나눠 먹는 싸움이고,
상한이 이미 잡힌다 — 참조 재사용은 조각당 몇 초, 상주 프로세스는 웜 기준 12초 남짓이다.

그리고 상주 프로세스는 **위험이 이득보다 크다**: 2.5GB 를 작업 사이에도 붙들면
이 앱이 스스로 정한 양보 정책(여유 4000MB 미만이면 CPU 로 내려간다)과
ComfyUI 병행 전제를 정면으로 깬다. CPU 로 떨어지면 문장당 30초라 개선이 아니라 재앙이다.

## ★생성 루프 안에서 확인한 낭비

벤더가 코덱 프레임마다 부르는 예측기에 `output_hidden_states=True` 를 준다.
그런데 결과에서 읽는 것은 `.sequences` 뿐이고, 은닉 상태는 **한 번도 쓰이지 않는다**
(바로 아래에서 임베딩으로 새로 만든다).

12Hz 기준 20초 음성이면 240 프레임 — 매 프레임마다 전 레이어 은닉 상태를 쌓고 버린다.
★**아직 고치지 않았다.** 재기 전에는 고치지 않는다.

## 이번에 한 것: 재는 자를 채웠다

재는 비용은 **이미 치르고 있었다** — 브리지가 단계마다 경과를 실어 보내고 있었고,
기록기에는 `stage_elapsed` 칸이 있었다. 문제는 둘 다 쓰이지 않은 것이다:
부모가 그 숫자를 읽지 않고 버렸고, 기록 칸은 **부르는 곳이 0건**이라 언제나 빈 배열이었다.

이제 네 칸이 남는다.

- `model_load` — 프로세스를 띄워 모델이 올라오기까지(**부모 시계**).
  파이썬 기동·torch import·가중치 읽기가 전부 여기 들어간다.
- `bridge_loaded` — 브리지가 제 시계로 잰 적재(**제가 뜬 뒤부터**).
- `bridge_generating` — 생성 시작까지.
- `run_job` — 전체. 조각별 생성 합과 견주면 "생성 밖" 이 바로 나온다.

★**두 시계를 섞지 않는다.** 부모는 "프로세스를 띄운 뒤" 를, 브리지는 "제가 뜬 뒤" 를
잰다. 브리지 값에는 기동·import 가 들어 있지 않다. 한 이름으로 합치면 숫자를 읽을 수 없다.

★없는 값을 0으로 적지 않는다 — 안 걸린 것처럼 보이는 쪽이 더 나쁘다.

## 다음 순서

1. 같은 대본·같은 참조·고정 씨앗으로 연속 2회씩 돌려 기준선을 잡는다.
   찬 실행과 더운 실행의 차이가 그대로 나온다.
2. 그 숫자로 `output_hidden_states` 낭비의 크기를 확정한다.
3. 고친 뒤 **같은 씨앗에서 결과 해시가 완전히 같은지** 확인한다.
   다르면 되돌린다 — 소리가 바뀌는 속도 개선은 개선이 아니다.

★참조 음성은 사용자 미디어를 쓰지 않는다. 앱에 있는 한국어 엔진으로 만들어 쓴다.

## 검증
게이트 **통과 9 · 실패 0**. 계측 계약 검사 7건.

# 실측 결과 (2026-09-25, 사용자 승인 후 실제 합성 수행)

참조 음성은 **사용자 파일을 쓰지 않고** 앱의 한국어 엔진으로 만들었다.
씨앗 고정, 앱과 같은 파이썬, 같은 참조.

## 기준선 — 시간이 어디로 가는가

짧은 대본(1조각): 벽시계 21.3 / 21.9초 · 적재 8.3 / 8.3 · 생성 9.8 / 10.5
긴 대본(1조각): 벽시계 65.8 / 63.9초 · 적재 8.4 / 8.7 · 생성 54.2 / 52.0

- **생성 밖 고정비가 11.5초로 일정**하고, 그중 **적재가 8.4초**다.
- 짧은 합성에서는 적재가 **전체의 40%**, 긴 합성에서는 13%다.
- 생성은 대본 길이에 비례한다(짧은 쪽 10초, 긴 쪽 53초).

★**첫 실행은 적재가 35.5초였다.** 파일 캐시가 차가울 때다 — 데워지면 8.4초로 일정해진다.
  앱을 오래 안 쓰다 처음 합성하면 그 35초를 다시 낸다. 이것이 사용자가 체감하는 "처음이 느리다" 다.

## ★시도했으나 **이득이 없어 되돌린 것** — 은닉 상태 생략

벤더가 코덱 프레임마다 은닉 상태를 전부 쌓는데 결과에서 한 번도 읽지 않는다.
이론적으로는 명백한 낭비다. 감싸서 끄고 재 봤다.

1차(각 2회): 생성 시간 평균 **−1.5%**. 그런데 회차 간 변동이 4%라 판단 불가.
2차(같은 대본 8회, **켜고 끄기를 번갈아**): 은닉 유지 중앙 52.62초, 생략 중앙 52.23초 —
**차이 +0.7%**, 개별 값이 51.1~57.3초로 12% 퍼져 있다.

**결론: 실재하는 낭비지만 측정 가능한 이득이 없다.** 되돌렸다.

★왜 이론과 달랐나: 그 예측기는 프레임마다 몇 스텝만 도는 **작은** 서브모델이라,
쌓이는 은닉 상태의 양이 전체 계산에 비하면 미미했다.

★**소리는 8회 내내 완전히 같았다**(해시 한 종류). 즉 안전한 변경이긴 했다.
그래도 남기지 않는다 — **재서 이득이 없는 최적화를 코드에 두면**, 다음 사람이
"이게 왜 있지" 를 모른 채 유지 비용만 낸다. 대신 시도했다는 사실을 여기 적어
같은 실험을 다시 하지 않게 한다.

## 남은 후보와 각각의 상한

- **적재 8.4초/작업** — 짧은 합성의 40%. 프로세스를 살려 두면 없앨 수 있지만,
  2.5GB 를 작업 사이에 붙들어 앱의 GPU 양보 정책(여유 4GB 미만이면 CPU)과
  ComfyUI 병행 전제를 깬다. CPU 로 떨어지면 문장당 30초라 **개선이 아니라 재앙**이다.
  하려면 유휴 해제와 다른 GPU 작업 전 강제 반납이 반드시 함께 와야 한다.
- **조각마다 참조 재인코딩** — 이번 벤치는 두 대본 모두 **1조각**이라 이 항목이
  드러나지 않았다. 이득은 조각 수에 비례하므로 **조각이 여럿인 재료로 다시 재야** 한다.
- **생성 자체** — 시간의 대부분이지만 줄이려면 배치 생성이나 모델 수준 변경이고,
  둘 다 소리가 바뀔 수 있다. 품질을 깎는 개선은 개선이 아니다.

## 이번에 남긴 것

- `python/bench_tts.py` — 사용자 미디어 없이 합성 속도를 재는 자. 씨앗 고정,
  결과 해시 비교, 찬/더운 구분.
- 계약 검사 8건 — 특히 "사용자 파일을 받는 통로가 없다" 와 "결과 해시를 남긴다".
  ★속도만 재고 소리를 안 보면 **소리가 바뀐 개선을 개선으로 착각한다.**

## 검증
게이트 **통과 9 · 실패 0**. 실제 합성 12회 수행(GPU), 결과 해시 전부 일치.

# 2차 실측 — 조각이 여럿일 때 (합성 4회 추가, 누적 16회)

1차에서는 두 대본 모두 **1조각**이라 "조각마다 반복되는 준비" 를 보지 못했다.
조각이 갈리는 재료를 더해 다시 쟀다.

## 결과: 그런 비용은 **없다**

적재와 생성을 뺀 나머지가 **조각 수와 무관하게 일정하다.**

- 1조각 8회: 나머지 3.08~3.25초
- 2조각 3회: 나머지 3.37~3.38초

조각이 두 배가 돼도 0.2초밖에 안 늘었다. 조사가 지목한 "조각당 반복 비용" 은
**측정상 존재하지 않는다.**

★한 실행만 8.82초로 튀었는데, 그때는 적재가 31.9초였다 — 파일 캐시가 차가운 실행이다.
  2점 관측으로 "조각이 늘어 고정비가 늘었다" 고 읽었다면 틀린 결론을 냈을 것이다.

## 참조 재인코딩도 재 봤다 — 생성의 0.72%

벤더가 조각마다 참조를 다시 읽고 다시 인코딩한다. 계측기를 달아 쟀다.

- 첫 조각: 1.062초 (1회)
- 둘째 조각: **0.047초** (1회)
- 합계 1.11초 = 생성의 **0.72%**

둘째 조각이 첫 조각의 1/22 이다 — 즉 첫 호출에 워밍업이 몰려 있고 반복 자체는 싸다.
**없앨 수 있는 최대치가 0.05초**다. 고칠 값어치가 없다.

## ★조사가 지목한 "생성 밖" 항목 셋이 전부 실측에서 무너졌다

| 항목 | 이론 | 실측 |
|---|---|---|
| 은닉 상태 낭비 | 프레임마다 쌓고 버림 | +0.7% (잡음) |
| 참조 재인코딩 | 조각마다 반복 | 0.72%, 절약분 0.05초 |
| 조각당 고정비 | 조각 수에 비례 | 0.2초/조각 |

**이론적 낭비와 측정 가능한 비용은 다르다.** 세 번 연속 그랬다.

## 확정된 시간 구조 (16회 실측)

```
합성 시간 = 적재 8.4초 + 생성(대본 길이 비례) + 나머지 3.2초
```

- 짧은 합성 21초: 적재 **39%** · 생성 46% · 나머지 15%
- 긴 합성 64초: 적재 13% · 생성 **82%** · 나머지 5%
- 아주 긴 합성 165초: 적재 5% · 생성 **93%** · 나머지 2%

★찬 시작이면 적재가 **31.9~35.5초**다(평소 8.4초).

## 남은 후보는 둘뿐이고, 둘 다 쉽지 않다

1. **적재 8.4초** — 짧은 합성의 39%. 없애려면 프로세스를 살려 둬야 하는데,
   2.5GB 상주가 GPU 양보 정책과 ComfyUI 병행 전제를 깬다.
   ★다만 **찬 시작 35초**는 다른 각도가 있다 — 앱을 켤 때 미리 데우면
   사용자가 기다리는 시간이 아니라 **배경에서** 지나간다. 상주와 달리 VRAM 을
   붙들지 않는다(파일 캐시만 데운다).
2. **생성** — 긴 합성의 82~93%. 줄이려면 배치 생성이나 모델 수준이고, 둘 다 소리가
   바뀔 수 있다. 품질을 깎는 개선은 개선이 아니다.

## 남긴 계측

참조 준비 계측은 **유지한다**. 지금은 0.72%지만 참조가 길어지거나 조각이 많아지면
커지고, 그때 바로 보인다. 은닉 상태 실험처럼 **같은 것을 다시 재지 않으려면**
자가 남아 있어야 한다. 비용은 래퍼 하나이고 소리가 바뀔 통로가 없다(검사로 못박음).

## 검증
게이트 **통과 9 · 실패 0**. 계측 계약 검사 10건. 실제 합성 누적 16회.
