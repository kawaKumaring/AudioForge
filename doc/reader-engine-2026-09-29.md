# 낭독 엔진 — 무엇을 어떻게 만들었나 (2026-09-29)

관리자가 GUI 를 세우고(`doc/reader-ui-handoff-2026-09-29.md`) 엔진을 넘겨받았다.
이 문서는 **왜 이렇게 만들었는지**와 **아직 안 한 것**을 적는다.

---

## 1. 실측이 설계를 정했다

기본 목소리(piper)로 글자 수를 늘려 가며 쟀다(`scripts/measure-read-aloud-speed.mjs`).

```
만드는 시간 = 1.81초(고정) + 소리 길이 × 0.0322
```

- 고정비를 뺀 실질 속도 **31배 실시간**
- 그런데 **한 번 부를 때마다 1.8초를 버린다**

그래서 덩이 크기가 전부를 가른다.

```
 5초 분량 → 2.0초에 만든다 · 배수 2.5
10초 분량 → 2.1초 · 배수 4.7
20초 분량 → 2.5초 · 배수 8.2
60초 분량 → 3.7초 · 배수 16.1
```

★**10자 한 문장은 0.82배** — 읽는 속도보다 느렸다. 소설은 줄이 짧아 줄 단위로
만들면 오히려 끊긴다. 그래서 **표시용 문단과 합성용 덩이를 따로** 둔다.

참조 목소리는 다르다. 다섯 명 생성 자료로 계산하면
`45초(고정) + 소리 길이 × 2.47` — 고정비를 빼도 **0.4배**다.
10분 들으려면 25분을 만들어야 한다. **실시간이 아니다.**
지금 구조로 동작은 하지만 계속 기다리게 된다.

## 2. 무엇이 어디에 있나

- `src/shared/readerChunks.ts` — **나누기 규칙.** 15~30초 분량으로 모은다.
  원문 글자 자리를 들고 다녀 본문 표시·건너뛰기를 잇는다.
  문장 한가운데를 자르지 않고, 문장 부호 뒤 따옴표를 떼어 놓지 않는다.
  한 문장이 최대치를 넘으면 **그대로 둔다** — 늦는 것이 끊기는 것보다 낫다.
- `src/shared/readerQueue.ts` — **앞서 만들어 두는 판단.** 시계도 GPU도 없이 검사된다.
- `src/main/ipc/reader.ipc.ts` — 덩이 하나를 소리로. 글+목소리 지문으로 쌓아 둔다.
- `src/renderer/hooks/useReadAloud.ts` — **잇기만** 한다. 판단은 위 둘이 갖는다.
- `src/renderer/components/ReaderWorkspace.tsx` — 화면(관리자 작업 + 배선).

## 3. 지키는 규칙

- **한 번에 하나만 만든다.** 본체가 파이썬을 하나만 돌린다 — 판정은 `synthesisGate` 하나.
  ★**아직 반쪽이다**(같은 날 재조사). 낭독은 시작 전에 남을 **보기만** 하고, 제가 돈다는
  표시를 줄에 남기지 않는다. 그래서 참조 목소리로 읽는 동안 다른 화면의 합성이 시작될 수 있다.
  멈춰도 돌던 파이썬은 끝까지 간다. — 고칠 목록 3번.
  ★낭독**끼리**는 9-30 부터 한 줄로 선다(`createLane`). 예전에는 목소리를 바꾸면 둘이 같은 자리에
  같은 이름으로 쓰다가 하나가 죽었다 — 사용자 신고로 재현했다. 작업마다 제 폴더를 쓴다.
- 목소리를 바꾸면 **곧바로** 옛 소리를 멈추고 같은 자리를 새 목소리로 다시 읽는다.
- 기본 목소리는 **누르기 전에도** 고른 자리부터 덩이 셋을 만들어 둔다. 참조 목소리는 누를 때만.
- **앞선 것부터** 만든다. 뒤엣것을 먼저 만들면 소용없다.
- 자리를 옮기면 **지나온 것은 버린다.** 긴 책에서 자리만 차지한다.
- 목소리가 바뀌면 만들어 둔 것은 **전부 무효.** 늦게 온 옛 결과도 받지 않는다.
- 소리는 **한 번에 한 곳만** — 공용 규칙에 `reader` 로 참여한다.
- 책과 읽던 자리는 **파일 하나씩**(`works/books/`). 빼면 그 파일만 지운다.
- 쌓아 둔 조각은 앱 데이터 자리(`readerChunks/`). 400MB 를 넘으면 오래된 것부터 지운다.
  **결과 폴더가 아니다** — 캐시다.

## 4. 만들면서 잡은 결함 셋

1. **화면이 소리 주소를 직접 만들었다.** 파일은 멀쩡히 만들어졌는데 열지 못했다.
   주소는 본체에게 묻는다(`getFileUrl`). 검사가 "재생을 시작하지 못했습니다" 로 잡았다.
2. **큐가 바뀔 때마다 같은 덩이를 다시 틀었다.** 뒤엣것을 만들어 두면 `items` 가
   바뀌는데 그때마다 재생이 처음으로 돌아갔다. 무엇을 틀었는지 기억하게 했다.
3. **거절당한 덩이가 '실패' 로 굳었다.** 다른 작업이 끝나도 풀리지 않아 그 자리에
   갇혔다. 다시 누르면 푼다(`retryFailed`). 그 길이 있는지 계약 검사가 붙든다.

### 4-1. 사용자가 찾은 결함 (같은 날 저녁)

4. **개발 실행에서는 한 소리도 나지 않았다.** StrictMode 가 화면을 붙였다 떼었다 다시 붙이는데,
   엔진은 뗄 때 '살아 있음' 을 끄고 다시 켜지 않아 만든 소리를 전부 버렸다.
   재현 — StrictMode 밖 재생 8/8 · 안 **0/8**. 앱 검사는 배포 빌드라 보지 못했다.
   → `reader-aloud.component.mjs` 가 React 개발판 + StrictMode 로 엔진을 돌린다(게이트).
5. **목소리를 골라도 그 덩이가 끝날 때까지 옛 목소리였다.** 곧바로 바꾼다.
6. **여는 자리를 운영체제가 정했다.** 브라우저식 파일 입력칸 때문이다 — 본체 대화상자로
   바꾸고 글(`lastTextDir`)·목소리(`lastVoiceDir`, 앱 공용) 폴더를 기억한다.
   화면에 그런 입력칸이 다시 생기면 `dialogFolders.test.ts` 가 울린다.
7. **막 시작한 재생을 멈춤이 끊으면 낭독이 꺼졌다.** 브라우저의 AbortError 를 실패로 읽었다 —
   목소리를 바꾸거나 읽는 중 문단을 누르는 순간이 겹치면 걸렸다(10번 중 1~5번). 실패로 보지 않는다.
8. **개발 실행에서 같은 요청이 두 번 나갔다.** 같은 목소리·같은 글이면 가 있는 답을 함께 받는다.
9. **(9-30) 둘이 동시에 돌면 하나가 죽었다.** 같은 작업 폴더·같은 이름에 썼다 — 한 줄로 세우고 제 폴더를 쓴다.
10. **(9-30) 참조 목소리는 0초 만에 거절당했다.** 입력 칸을 비워 보냈다 — 목소리 파일을 입력으로 넘긴다.
11. **(9-30) 실패하면 실행 명령줄이 붉게 번쩍이고 사라졌다.** 파이썬의 사유를 보이고(경로는 이름만),
    멈춘 뒤 자리 맞추기가 문구를 지우지 않게 했다. 실패는 로그 `reader` 에 남는다(글 내용 없이).

### 4-2. 읽는 구절 · 괄호 속 한자 (같은 날 지시)

- **읽는 구절** — 지금 덩이의 글자 자리(start/end)로 문단 안에서 그만큼만 칠하고, 덩이가 넘어가면
  가운데로 가져온다. 끄는 단추는 아래 막대의 '따라가기'. 문장 단위는 소리 안 시각이 없어 하지 않았다.
- **괄호 속 한자** — `src/shared/readerText.ts` 의 `speakableText`. 괄호 안이 한자뿐일 때만 뺀다.
  보이는 글은 그대로이고 소리로 보낼 때만 탄다. 본체의 쌓아 두기는 '목소리 + 실제로 읽은 글' 로
  이름 붙으므로 한자가 없는 덩이는 설정을 바꿔도 다시 만들지 않는다. 큐는 설정까지 보고 바뀌면 다시 읽는다.
- 두 설정은 `readerPrefs` 한 칸(`doc/settings-format.md`).

### 4-3. 큰 책 · 글자 방식 (2026-09-30)

- **큰 책은 보이는 문단만 그린다** — `src/shared/readerWindow.ts`(자리 계산만 하는 순수 함수).
  3천 문단을 넘는 책만 쓴다. 3천 문단은 전부 그려도 누름 20ms · 열기 0.55초로 문제없었다(실측).
  실측(3만 문단 · 5.5MB): 전부 그리면 열기 3.7초 · 누름 120~170ms(거의 전부 브라우저의 배치·그리기) →
  창을 쓰면 열기 0.28초 · 누름 23~35ms. 9.8MB(5만 3천 문단)도 열기 0.34초 · 누름 약 45ms.
  - 높이는 글자 수로 어림하고, 그려진 문단은 실제 높이로 바꾼다. 위아래 1,200px 을 더 그려 둔다.
  - 그리지 않은 문단으로 가야 할 때(고른 자리 · 읽는 구절 따라가기) — 어림 자리로 먼저 굴리고, 그려진 뒤 실제 자리로 맞춘다.
  - ★`content-visibility: auto` 는 쓰지 않는다 — 열기는 2.0초로 줄었지만 문단마다 보임 감시가 붙어 누름이
    210~370ms 로 **늘었다**(보임 계산만 388ms/3회).
- **글자 방식** — `src/shared/readerDecode.ts`. 머리표(BOM) → 머리표 없는 UTF-16(0 바이트와 ASCII 의 짝) →
  UTF-8(엄격) → CP949(엄격) 순. 어느 것도 아니거나 읽은 글에 제어 문자가 섞이면 거절하고 사유를 말한다.
  ★CP949 확장 글자(똠 등)는 화면(크로미움)의 해독기에만 있다 — Node 의 해독기에는 없어 단위 검사로는 못 본다(실측).
  그래서 실제 앱 검사(`reader-encoding.e2e.mjs`)가 본다.

### 4-4. 기본 목소리 여럿 (2026-09-30)

- 지시: "기본 모델들을 여러 개 연결해 봐라, 하나씩 사용자가 들어 보고 선택하게."
- 조사한 후보 — Supertonic 3(목소리 10 · CPU · Open RAIL-M) · Qwen3-TTS 0.6B CustomVoice(9 · 한국어 Sohee · GPU · 2.5GB ·
  Apache-2.0) · MeloTTS-Korean(1 · MIT · 윈도우 설치가 무겁다). **Supertonic 3 을 붙였다** — 낭독은 앞서 만들어 두는 일이
  많아 CPU 이고 빠른 것이 맞다. 받아 적기로 확인: 열 목소리 모두 문장을 글자 그대로(일치 1.00, Whisper small).
  속도: 모델 열기 0.86초, 한 덩이(10초 분량) 1.7~2.0초 — 실시간의 5~6배.
- 목록·들어 보기·고르기·읽기는 원래 있던 길(`builtin_voices.py` → 설정 창의 줄마다 '▶ 들어 보기')을 그대로 탄다.
- ★아직 고른 적 없는 사람의 첫 기본 목소리가 **Supertonic 여성 1** 로 바뀐다(이름 순). 이미 고른 사람은 그대로.
- ★사람이 들어 보고 고르는 일은 남아 있다 — 받아 적기는 '말이 맞는가' 까지만 본다. 자연스러운지는 귀로 판단한다.

### 4-5. 참조 목소리 — 실시간 낭독인가, 미리 만들어 두기인가 (2026-09-30 실측 · 판단)

**재는 법** — `python/bench_tts.py --repeat 2`(참조는 piper 로 만든 소리 · 사용자 미디어 없음). 실행 기록의 단계별 시간에서
**생성 시간만**(`generate_sum`)과 그 밖(모델 열기 등)을 나눴다. 모델을 띄워 둔 채(상주) 읽으면 없어지는 것이 '그 밖' 이다.
Qwen3-TTS 0.6B Base · 이 기계의 GPU · 같은 조건 두 번씩(두 번의 차이 1초 안쪽).

- 소리 3.0초 — 생성 9.6초 · 전체 20.8초
- 소리 19.1초(한 덩이 크기) — 생성 56.0~57.0초 · 전체 67~68초
- 소리 54.1초 — 생성 152~155초 · 전체 163~166초
- 매번 드는 고정비 약 11초(모델 열기 8.2초 + 준비 약 3초). **생성만의 속도는 실시간의 0.35배.**

**판단 — 참조 목소리는 '미리 만들어 두기' 다.** 상주시켜도 덩이마다 11초만 준다(67초 → 56초). 20초 분량을 듣는 동안
다음 20초를 만들려면 생성이 실시간의 1배를 넘어야 하는데 0.35배다 — 듣다가 36초씩 기다리게 된다.
그래서 **상주 실행기를 만들지 않았다**(이득 약 16%에 비해 GPU 를 늘 붙드는 비용이 크다).
기본 목소리(Supertonic 5~6배 · piper)는 실시간으로 충분하다 — 지금 길 그대로.
- 같은 이유로 Qwen3-TTS CustomVoice(한국어 Sohee 등 9, GPU, 2.5GB)는 낭독용으로 받지 않았다 — 같은 엔진이라 같은 속도일 것이다(재지 않음).
- 다음 갈림길(사용자 결정): ① 참조 목소리로 **책(장) 전체를 미리 만들어 두는** 단추 — 만든 뒤에는 끊김 없이 듣는다,
  ② 생성 속도 자체를 올리는 조사(정밀도·주의 연산 구현 등 — 모델 교체 전에 구현을 본다). 둘 다 아직 하지 않았다.

### 4-6. Qwen 이 느린 까닭 — 코드와 실측 (2026-09-30)

**구조(모델 코드 `modeling_qwen3_tts.py` 1671행)** — 소리를 1초에 12.5 조각(프레임)으로 **앞에서부터 하나씩** 만든다.
조각 하나마다 본 모델(28층)이 한 걸음, 그 안에서 보조 모델(5층, 코드 묶음 16개 중 나머지 15개)이 **HuggingFace generate() 를 통째로 한 번**
불러 15 값을 차례로 만든다. 1초 분량 = 본 모델 12.5번 + 보조 모델 약 187번이 **순서대로**.
Supertonic 은 반대로 문장 전체를 한꺼번에 8번 다듬는다(순서대로 만드는 조각이 없다) — 그래서 CPU 로도 5~6배 빠르다.

**실측(소희 · 10.48초 분량 · 조각 132개 · RTX 5070 Ti · bfloat16 · sdpa)** — 구간마다 시계를 달아 잰 값(시계 때문에 전체가 약 30% 부풀었다 — 비율만 본다).
- 전체 생성 43.6초 중 **보조 모델 32.4초(74%)** — generate() 131번, 한 걸음 계산 1,965번(조각당 15번), 한 번에 평균 약 14.5ms.
  5층짜리 모델에 글자 하나를 넣는 일은 GPU 로 1ms 도 안 걸리는 크기다 → 시간은 계산이 아니라 **한 번 부를 때마다 드는 준비 비용**(파이썬·프레임워크 처리, GPU 명령 내려보내기)이다.
- generate() 준비 자체만 3.9초(131번 × 약 30ms).
- 본 모델 걸음 10.4초(132번, 걸음당 약 79ms). 소리 복원(코덱 → 파형)은 0.1초 — 문제 아님.
- GPU 사용률 평균 69% · 최고 86% — 작은 일을 쉼 없이 받지만 한 번에 조금씩이다.
- 매번 새 프로세스라 모델 열기 9.3초가 따로 든다(낭독은 조각마다).

**결론** — 느린 까닭은 GPU 가 약해서가 아니라 **만드는 방식**이다: 아주 작은 계산을 수천 번 순서대로 부르고, 부를 때마다 드는 비용이 계산보다 크다.
**손댈 수 있는 곳(아직 하지 않음 · 효과는 재지 않았다)** — ① 보조 모델의 generate() 를 직접 쓴 반복으로 바꾸기(준비 비용 3.9초는 확실히 사라짐)
② 정해진 15걸음을 CUDA graph 로 묶어 부르는 비용 줄이기(같은 병목을 푸는 공개 구현들이 쓰는 길) ③ 모델을 띄워 둬 조각마다 9초 열기를 없애기.
